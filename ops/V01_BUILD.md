# 통합 구현 지시서 (V01-20260902): Development OS v0.1 — 작동하는 최소 완성형

> **승인 범위**: 코드 구현 · 격리 테스트 · PR/브랜치 작성. 사소한 구현 보완은 재승인 없이
> 진행한다. **금지(운영 전환 승인 전)**: 운영 DB 적용, 운영 봇 교체, 자동 스케줄
> 활성화(pm2/cron/systemd 등록), main 병합, 새 유료 서비스 사용, 없는 권한 우회.
> auto-exec·영상 워커 정지 유지, `AUTO_EXEC_MODE` 불변.

## 시스템 정의 (범위 고정 — 대표 확정)

**Development OS = 매일 개발 능력·프로세스가 개선되는 공통 시스템.**
구운록 등 개별 프로젝트는 구축 범위에서 제외한다 (나중에 이 기반을 쓰는 대상일 뿐).
v0.1 완료 기준: **"공통 개발 프로세스 개선 1건을 스스로 발견 → Codex 검토 → 대표 승인 →
격리 구현·검증 → PR·알림 → 효과 기록까지 완주"** (완주 검증 자체는 운영 전환 승인 후).

구조: **development-os = 관제 본체** (레지스트리·오케스트레이터·지식·기록),
**Nexus(personal-os) = 텔레그램·승인 인터페이스** (P1 브랜치).
미루면 안 되는 최소 조건: 승인 없는 개발 차단 / 비밀 보호 / 격리 작업 / 무단 병합·배포
금지 / 실패 알림. 나중으로 미루는 것: 다중 프로젝트 우선순위, 정교한 지식 검색,
비용 최적화, 대시보드, 복잡한 재시도 정책.

## A. 중간 점검 결함 수정 (personal-os `pilot/approval-adapter` 이어서, 재승인 불요)

관제 세션의 실코드 검토에서 나온 결함 4건 — 수정 + 각각 테스트 추가:

1. **기록 실패의 침묵**: `recordDecision`/`applyProposalStatus` 실패가 console.error로
   삼켜지고 사용자에겐 "✅ 승인 접수"가 회신된다. 감사 기록 없는 승인 접수는 사고다.
   → DB 계층이 실패를 반환/throw하게 바꾸고, 실패 시 회신을 "⚠️ 결정을 기록하지 못했습니다
   — 처리되지 않았습니다. 다시 시도해 주세요"로. audit에도 failed로.
2. **오류≠미존재 혼동**: `getLatestProposal`이 DB 오류와 미존재를 모두 null로 돌려
   "ID를 확인해 주세요" 오안내가 나간다. → 오류를 구분해 "조회 실패(일시 오류)" 회신.
3. **동시 결정 보강**: `applyProposalStatus`에 낙관적 조건(`.eq("status", <판정 시점의
   status>)`)을 걸어, 판정과 반영 사이에 상태가 바뀌었으면 반영하지 않고 재시도 안내.
4. **dedup 경합**: `insertEvent`가 unique 충돌로 실패하면 id:-1로 발송을 진행해 중복
   발송 가능. → 충돌 시 기존 행을 재조회해 deduped 처리.

## B. development-os 본체 구현 (신규)

`~/development-os`에 로컬 git 저장소로 구현한다 (원격 저장소는 대표가 생성하는 대로
push — 그때까지 로컬 커밋 유지, 원격 생성은 착수를 막지 않는다).

구성 (구현 재량 허용 — 아래는 요구 기능이지 파일 구조 강제가 아님):

1. **레지스트리**: 프로젝트 다중 등록 가능한 형식(yaml/json). v0.1 등록 대상은
   **dev-process(시스템 자신) 1건만**. 각 항목: 이름·저장소·방향·금지사항·상태.
2. **일일 사이클 오케스트레이터** (v0.1은 **수동 트리거 CLI로만** 실행 — 스케줄 등록 금지):
   - **조사**: 서버 claude headless(제한 도구: 읽기+웹)로 최신 개발 기술·도구·자동화
     방법을 조사하고, 현재 우리 프로세스(이 시스템 자신의 운영 기록·결함 목록)와 비교.
   - **제안**: 가치 있는 개선이 있으면 **하루 최대 1건** dev_proposals에 draft 생성
     (없으면 0건이 정상 — 억지 제안 금지). 제안 본문에 근거·완료 조건·위험·예상 범위.
   - **Codex 기획 검토**: `codex exec` 가능하면 검토 실행 → passed/failed + 출력 보존.
     불가하면 `not_performed` + 미충족 사유 유지 — **이 상태로는 승인이 차단되는 것이
     정상 동작이다. 검토를 건너뛰는 우회 코드를 만들지 마라.**
   - **발송**: 텔레그램으로 제안 발송(P1 notifyOwner 계열 재사용 — personal-os 코드를
     로컬 경로 import하든 최소 복제하든 재량, 단 봇 토큰·발송 기록 규칙은 동일하게).
   - **승인 감지 → 격리 개발**: `approved`(is_test=false, codex passed) 제안을 감지하면
     Context Pack(제안 본문+대상 저장소+기준 커밋+완료 조건+금지 목록)을 만들어
     **격리 worktree에서** claude headless(`dontAsk` + 작업별 허용 도구, 비밀 경로 차단)
     로 구현 → 테스트 → Codex 검수(가능 시) → **브랜치 push + PR(불가 시 compare URL)**
     → 텔레그램 완료 알림. main 병합·배포는 하지 않는다.
   - **기록**: 사이클마다 비용·토큰(`modelUsage` 합산, 추정치 명시)·실패·결과를
     기록 파일/테이블에 남기고, 채택·기각된 개선은 knowledge에 상태 태그로 축적.
3. **알림**: 승인 요청 외 완료/실패/조치 필요도 텔레그램 발송 + report_written과
   tg_status 별도 기록 (P1 규칙 동일).
4. **DB**: 추가로 필요한 테이블(예: dev_task_metrics, dev_cycles)은 **마이그레이션 파일
   작성까지만** (적용은 운영 전환 승인).

## C. 격리 검증 (운영 무영향 — 이번 범위에서 수행)

1. **SDK 실차단 시험 4종** (격리 sandbox, P1 봇의 도구 구성 그대로): ① 파일 수정 요청
   → 해시 불변+거부 기록 ② Bash 요청 → 거부 ③ `.env` 읽기 요청 → canUseTool 거부
   ④ 프로젝트 훅 미로드 확인. **여기서 통과해야 비로소 "차단된다"로 기록 가능.**
2. **DB 통합 시험**: 운영 Supabase 금지. 로컬 임시 postgres(pglite 등 무료 npm 패키지
   재량 — 유료 서비스·글로벌 설치 금지)에 068 + 신규 마이그레이션을 적용해 승인
   왕복(승인/거절/수정/중복/구버전/Codex 차단)을 DB까지 통합으로 검증.
3. **오케스트레이터 드라이런**: 조사→제안 생성→발송 직전까지를 dry-run 모드로 실행,
   생성물(제안 초안·Context Pack)을 보고서에 첨부. 텔레그램 실발송이 필요한 시험은
   `[시험]` 접두를 붙여 **1~2회로 제한** (sendMessage만 사용 — 폴링 충돌 없음).
